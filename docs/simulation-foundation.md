# حالة الإصدار الأول للمراجعة

نُفذت هذه التغييرات على فرع مستقل مبني على main عند 0a89d1b71bf3be6045accf87670130857687a3b3. نجح فحص TypeScript والبناء واختبارات Python مع PostgreSQL تجريبي، واختبار HTTP يشغّل API وعامل المحاكاة في عمليتين منفصلتين. لم يُنفذ نشر إنتاج، ولا يعني نجاح الاختبارات جاهزية إطلاق تجاري عام.

المعاينة البصرية داخل المتصفح واختبار الهاتف لم يُتح التحقق منهما في بيئة التنفيذ. لم تُستدعَ نماذج مدفوعة ولم يُنفذ تدريب أوزان أو اختبار جودة توليد حي. تبقى مراجعة الواجهة وقبول النتائج ببيانات حقيقية وتشغيل العامل في بيئة تجريبية خطوات مطلوبة قبل النشر.

# نمل — أساس المحاكاة ومساحة العمل التجارية

## نطاق هذه المرحلة

- واجهة محاكاة اختيارية مستقلة؛ فتحها وحفظ المدخلات لا يشغلان المحرك.
- قالبان: خط إنتاج ومسار معاملات. كلاهما يستخدم عقد بيانات واحدًا لمراحل متتابعة، طوابير FIFO غير محدودة، موارد متوازية لكل مرحلة، وصول منتظم، وزمن خدمة ثابت أو مثلثي.
- نسخ سيناريوهات غير قابلة للتعديل بعد الحفظ. النسخة المعدلة ترتبط بالأصل، وتثبت كل تجربة المدخلات وبصمتها ونسخة المشروع والبذرة وعدد التكرارات.
- نتائج فعلية باستخدام SimPy: المكتمل والمتبقي والإنتاجية وزمن الإنجاز وانتظار المراحل وانشغال الموارد. النطاق المعروض أدنى وأعلى التكرارات، وليس فترة ثقة أو احتمال نجاح في الواقع.
- المهام الداخلية تشترك افتراضيًا في نموذج الأساس الذي حدده المدير، مع اختلاف التخصص والنطاق. إعداد الإدارة execution.shared_worker_model=false يعيد اختيار محرك لكل تخصص.
- سجل داخلي متسلسل لتسليم المهام، محاولاتها واعتماداتها وبصمة سياقها ومراجع النتائج. اكتمال المهمة لا يرقّي مخرجاتها إلى حقائق مؤكدة.
- واجهات الجلسات والمحادثات تعيد قائمة حقول مخصصة للعملاء، وتحتفظ بالتفاصيل التشخيصية للمشرف. إعدادات النماذج على مستوى الحساب والمشروع للمشرف فقط.

## تشغيل التطوير

المتطلبات المعتادة في requirements-dev.txt وتشمل SimPy المثبت على 4.1.2.
شغّل API المعتاد، ثم عملية منفصلة:

```sh
export NAML_SIMULATION_ENABLED=true
python -m agent_system.simulation.worker
```

اضبط NAML_SIMULATION_ENABLED=true على كل من API والعامل. يُترك false افتراضيًا.
على جهاز واحد يمكن مشاركة ملف SQLite نفسه بواسطة DATABASE_PATH المطلق.
على خدمات منفصلة يجب أن يشترك الطرفان في DATABASE_URL لنفس PostgreSQL؛ لا تستخدم قرصين محليين منفصلين.

لا توجد محاكاة داخل BackgroundTasks لطلب المحادثة. العامل يستعلم عن القائمة مرة في الثانية عندما يكون خاملًا.
لا تُقبل تجربة جديدة إذا لم تصل إشارة جاهزية العامل خلال آخر 30 ثانية، بينما يظل حفظ السيناريو متاحًا.
نشر العامل وتغيير إعدادات الإنتاج خطوات مستقلة لم تُنفذ ضمن هذا الفرع.

## حدود التشغيل

لكل تجربة: حتى 12 مرحلة، 5000 وحدة، 20 تكرارًا، وسقف 200000 وحدة × مرحلة × تكرار، ومهلة حساب 45 ثانية.
لكل حساب: تجربتان نشطتان و30 تشغيلًا في اليوم بتوقيت UTC، و200 تشغيل محفوظ و100 نسخة سيناريو في هذه المرحلة.
قائمة مشتركة محدودة بـ100 تشغيل نشط. يتطلب التوسع نقلها إلى جداول مفهرسة وعمال موزعين وضبط حصص وفوترة وسياسة أرشفة.
حجز العمل 120 ثانية، وبحد أقصى محاولتين عند انقطاع العامل. انتهاء الحجز أو الإلغاء يمنع نشر نتيجة متأخرة.
رقم طلب فريد يمنع التشغيل المكرر عند إعادة إرسال الطلب نفسه.
المحرك يقبل بيانات رقمية محققة فقط؛ لا يشغّل كودًا يولده نموذج أو يرسله مستخدم.

## حدود علمية ووظيفية

هذه البداية ليست محاكيًا لأي عملية بلا قيود. لا توجد في هذه المرحلة تفرعات مسار أو دفعات أو مخازن محدودة أو موارد مشتركة بين مراحل أو أعطال أو ورديات أو إعادة عمل أو تحسين رياضي تلقائي.
المقارنة الحسابية لا تثبت سببًا في الواقع. يجب معايرة أزمنة الخدمة والوصول والموارد والتحقق من النتائج ببيانات حقيقية قبل اتخاذ قرار تشغيلي.
زمن الإنجاز يخص الوحدات المكتملة فقط؛ الانتظار يخص من بدأوا الخدمة فقط، مع إظهار الطابور المتبقي منفصلًا.
اقتراح فتح المحاكاة داخل المحادثة لا يحول النص تلقائيًا إلى نموذج؛ المستخدم يراجع النموذج في الواجهة.
سجل تنسيق الفريق دائم، لكن استئناف مهام النماذج المتوقفة من منتصف التنفيذ وإعادة التخطيط الديناميكي غير منفذين هنا؛ تبقى سياسة استعادة الجلسات الحالية.

## حدود الفصل التجاري

إخفاء إعدادات وأحداث النظام في API هو حد الصلاحيات الفعلي؛ إخفاء الأزرار وحده لا يكفي.
لا يشمل هذا ضمانًا بأن المستخدم لن يستنتج التقنيات من السلوك، أو أن نصًا مولدًا لن يذكر تقنية عامة. لا تُرسل أسرار أو مفاتيح للنماذج أو للعميل.
تعطلت صفحات OpenAPI العامة. تحتفظ الإدارة بواجهاتها المحمية.
الشفافية بشأن الافتراضات ومصادر بيانات المهمة والحدود العلمية جزء من المنتج وتبقى ظاهرة.

## التحقق

أُضيف إعداد GitHub Actions لفحص TypeScript والبناء واختبارات Python وPostgreSQL، دون مفاتيح نماذج أو بيانات إنتاج. وجود ملف الإعداد لا يعني أن تشغيله على GitHub قد نجح؛ تُراجع نتيجة CI على الالتزام المرفوع نفسه.
الاختبارات تغطي حالة طابور بحل يدوي، توازن الوحدات، القص عند نهاية الأفق، أثر زيادة السعة، إعادة إنتاج العشوائية، منع العمل الزائد، تكرار الطلب، حجز العامل، الإلغاء، عزل الحسابات، وعقود الردود التجارية.
نجاح الاختبارات الآلية لا يغني عن اختبار قبول بشري على بيانات حقيقية ومراجعة صلاحيات النشر والفوترة قبل الإطلاق التجاري.

# نمل — NAML

مساحة عمل للمشاريع باستخدام مدير يختار مسار العمل ووكلاء عند الحاجة، بواجهة زجاجية عربية وحفظ دائم للمحادثات والمشاريع ولوحات العمل.

## تحديث 22 أكتوبر 2026 — الاستجابة وتوزيع العمل

- السؤال البسيط: استدعاء واحد للدور السريع يتضمن التوجيه والإجابة، دون تخطيط أو فريق أو مراجعة إلزامية. لا توجد إجابات ثابتة مخزنة لسؤال «عاصمة فرنسا»؛ يجيب النموذج المختار.
- الشرح أو الصياغة أو البرمجة المعتادة: توجيه، ثم نموذج واحد. البحث: توجيه، بحث، إجابة مستندة إلى النتائج وتلخيص، دون إنشاء خطة فريق كاملة. تضاف المراجعة عند الحاجة.
- ألغيت تعليمات إلزام المراحل السبع وإلزام الإجابة الشاملة. الاختصار افتراضي، وطلب المستخدم للتفصيل أو الكود الكامل يظل مقدمًا. يوجد اختيار «مختصر / تفصيلي» بجوار الإرسال.
- Enter يرسل؛ Shift+Enter يضيف سطرًا. لا يُرسل أثناء تركيب الحروف بلوحة إدخال IME.
- في إدارة النظام ← النماذج والإعدادات، بطاقة **الاستجابة وتوزيع العمل** تربط أدوار التوجيه والتنفيذ والبحث والمراجعة بإعدادات النماذج الموجودة. يمكن أن تكون الأدوار من Groq وOpenRouter في المهمة نفسها.
- افتراضيًا يستخدم التوجيه دور `fast`. إذا اخترت مديرًا خاصًا للحساب أو المشروع، يُحترم هذا الاختيار أيضًا للتوجيه والإجابة المباشرة. اضغط «استخدام الإعدادات الافتراضية» للعودة للدور السريع العام.
- التحويل الاحتياطي مغلق افتراضيًا. اختيار دور بديل يسمح بمحاولة واحدة إضافية عند 429 أو عطل مؤقت 5xx/اتصال، وقد يستهلك رصيد ذلك المصدر. لا يُحوّل خطأ المفتاح أو النموذج غير المتاح إلى مصدر آخر خفية.
- تُحترم مهلة `Retry-After` مع منع طلبات جديدة للنموذج نفسه خلال المهلة. لا يوجد تدوير مفاتيح أو حسابات لتجاوز الحصة. حد التزامن محلي لعملية الخادم الواحدة؛ لا يغني عن حدود المزود ولا عن منسق موزع عند تشغيل عدة نسخ.
- لكل مهمة سقف استدعاءات ومهلة تمنع بدء استدعاءات جديدة بعد انقضائها. تُضبط مهلة الشبكة بحسب الوقت المتبقي؛ هذا ليس إيقافًا قسريًا أو ضمانًا زمنيًا لكل عملية بحث/شبكة.
- تعرض «تفاصيل التنفيذ» عدد المحاولات، والزمن، والنموذج والمصدر، والتوكن المبلغ عنه. بيانات التوكن الناقصة توسم صراحة؛ لا تُعرض تقديرات مالية باعتبارها فاتورة. عند تفعيل اقتراح اللوحة، تسجل محاولته أيضًا وقد تظهر بعد تحديث الصفحة.
- الفرق تنفذ الأجزاء المستقلة بالتوازي وتنتظر الاعتمادات المصرح بها. الاعتمادات الدائرية مرفوضة، وفشل مهمة يمنع تشغيل المهام المعتمدة عليها.
- الأسئلة المباشرة والاستيضاحات لا تستدعي توليد اقتراح لوحة إضافي. الطلبات الأخرى تفعل ذلك فقط إذا صنفها الموجه مرتبطة بالمشروع وكانت ميزة الاقتراح مفعلة.

لا يتطلب هذا التحديث استضافة نماذج أو Chromium. لم تُضف بعد خدمة المتصفح أو تشغيل الكود المعزول أو طابور دائم مستقل؛ هذه مراحل تالية.

## دورة العمل الجديدة

- **فهم المشروع:** الهدف، معيار النجاح، القيود والموارد، والمرحلة الحالية محفوظة مع المشروع.
- **ذاكرة مصنفة:** أقسام للحقائق والافتراضات والأسئلة والقرارات والمهام والنتائج. الحقائق المقترحة تبقى غير متحقق منها؛ تأكيد المستخدم ليس تحققًا مستقلًا.
- **توجيه تكيفي:** يختار دور التوجيه استيضاحًا (حتى سؤالين)، أو إجابة مباشرة في الاستدعاء نفسه، أو تنفيذًا بنموذج واحد، أو بحثًا، أو فريقًا. قد يخطئ النموذج في اختيار المسار؛ تُعرض بيانات التنفيذ للمراجعة.
- **قرار ثم مهمة:** القرار المقترح يحتاج اعتمادًا صريحًا من «متابعة المشروع» قبل إنشاء مهمة مرتبطة. للمهام مسؤول وموعد ومخرج متوقع واعتماد على مهام أخرى. يمنع التطبيق الاعتمادات الدائرية وإكمال مهمة قبل متطلباتها.
- **نتيجة ثم مراجعة:** أضف قسم «النتائج والقياس»، واربط كل نتيجة بمهمة. أدخل المستهدف والفعلي والوحدة واتجاه المقارنة. الفراغ يعني غياب البيانات؛ الصفر قياس فعلي. يحفظ زر المراجعة لقطة للمقارنة، ولا يستنتج السببية أو نجاح المشروع كله.
- **التعامل مع التعثر:** يعرض المتابعة القرارات المنتظرة والعوائق والأسئلة والقياسات الناقصة والخطوة التالية. لا توجد مراقبة مجدولة في الخلفية أو تنفيذ أعمال خارجية أو إرسال رسائل تلقائيًا.
- **فشل النماذج:** فشل جميع الوكلاء يُوقف التحليل بحالة فشل واضحة. عند الفشل الجزئي تُستبعد الأخطاء من أدلة التلخيص ويظهر تنبيه. لا تُعرض نسب الثقة التخَمينية بوصفها قياسًا للدقة.

### معالجة إعدادات النماذج القديمة

1. افتح **إدارة النظام ← النماذج والإعدادات**. البدائل المقترحة تظهر للإعدادات القديمة المعروفة؛ راجعها ثم اضغط «تطبيق البدائل المعروضة» إذا رغبت.
2. عند تعديل نموذج، أدخل معرّفه يدويًا أو اضغط «جلب قائمة» للاستعلام من المزود. التوفر قد يختلف بحسب حسابك.
3. زر «اختبار» بجانب دور النموذج يرسل طلبًا قصيرًا فعليًا، وقد يُحتسب من رصيد المزود. نجاح اتصال المزود لا يعني أن كل نموذج متاح.
4. الإصلاح يشمل مدير النظام والوكلاء فقط. إذا خصصت مديرًا في إعدادات حسابك أو مشروعك، حدّث اختياره هناك أيضًا.
5. اختر دوري البحث والمراجعة من بطاقة «الاستجابة وتوزيع العمل». يُحافظ على دور `critic` القديم عند وجوده قبل التحديث. البديل اختياري ومغلق افتراضيًا.

النماذج الافتراضية للتثبيت الجديد: Groq `openai/gpt-oss-120b` للمدير والتحليل و`openai/gpt-oss-20b` للعمل السريع. الإعدادات المحفوظة السابقة لا تُستبدل تلقائيًا. قائمة الاقتراحات ليست ضمانًا لاستمرار توفر النموذج.

## الواجهة والمشاريع واللوحات المتكيفة

- واجهة زجاجية فاتحة، قائمة جانبية ثابتة على الكمبيوتر وقائمة قابلة للفتح على الجوال.
- إعدادات النموذج المدير محفوظة لكل حساب: Groq أو OpenRouter مع معرّف النموذج. يمكن إدخال معرّف آخر يدعمه المزود؛ القائمة المرفقة أمثلة وليست استعلامًا حيًا عن نماذج المزود.
- إنشاء مشاريع بأسماء وأهداف، وربط محادثات سابقة غير مرتبطة، وبدء عدة محادثات داخل المشروع.
- تخصيص نموذج مدير للمشروع أو تركه يتبع إعدادات الحساب. ترتيب الاختيار: المشروع ← الحساب ← إعدادات مدير النظام. يُثبّت اختيار التشغيل عند إرسال الرسالة.
- تبويبات لمتابعة المشروع والمحادثات ولوحة المشروع والإعدادات. اللوحة تبدأ بالمهام والملاحظات والقرارات.
- بعد رد مرتبط بالمشروع يتجاوز السؤال المباشر، يمكن للنموذج اقتراح أقسام وعناصر وفق العمل: المتطلبات والأخطاء والمراحل والمنتجات والمحتوى والمصادر والفصول والدروس والاختبارات. المحادثة العادية لا تُنشئ مشروعًا تلقائيًا.
- الاقتراح يظهر للمراجعة، مع مقتطف حرفي ورابط إلى الرسالة الأصلية لكل عنصر. تُرفض العناصر التي لا تستشهد برسالة موجودة ومقتطف مطابق، والروابط التي لا تظهر في الرسالة. القرارات تحتاج رسالة من المستخدم. هذه قيود تحقق وليست ضمانًا لدقة استنتاج النموذج؛ راجع الاقتراح قبل اعتماده.
- اعتماد الاقتراح يضيف العناصر دون استبدال العناصر الحالية. يمكن تجاهله أو إيقاف الاقتراحات أو تثبيت اللوحة.
- إضافة وتعديل وحذف العناصر، الحالة والموعد والرابط، إظهار الأقسام وإخفاؤها وتحريكها، والتراجع عن آخر خمسة تغييرات للوحة. التثبيت يمنع اقتراحات نمل وتطبيقها، ويسمح بتعديلاتك اليدوية.
- إصدارات للوحة تمنع الكتابة فوق تحديث متزامن؛ عند التعارض حدّث الصفحة ثم أعد المحاولة.
- إدراج محتوى ملفات TXT وMD وCSV في الرسالة فعلًا (حد الملف 60 كيلوبايت، وحد الرسالة كلها 20000 حرف). لا يدعم هذا الإصدار قراءة PDF أو الصور أو ملفات Office.

### تجربة الفكرة

1. افتح «الإعدادات» واختر المزود ومعرّف النموذج، ثم احفظ.
2. افتح «المشاريع ← مشروع جديد»، وأدخل الاسم والهدف.
3. ابدأ المحادثة داخل المشروع. بعد اكتمال الرد، افتح «لوحة المشروع» لمراجعة الاقتراح؛ وقد يحتاج بضع لحظات إضافية.
4. اعتمد الإضافات أو تجاهلها، ثم عدّل العناصر ورتّب الأقسام من «تخصيص».
5. أعد فتح المشروع في جلسة لاحقة؛ ستجد المحادثات واللوحة محفوظة.

توليد اقتراح اللوحة يستهلك طلبًا إضافيًا من النموذج المدير بعد الرد الناجح، ويمكن تعطيله لكل مشروع. لا يُنشأ اقتراح تلقائي جديد ما دام اقتراح سابق ينتظر المراجعة. عند ربط محادثة قديمة، استخدم زر «اقتراح تطوير اللوحة» أو تابع الحوار. لا توجد أرقام تجريبية في اللوحة ولا اتصال تلقائي بمتاجر أو خدمات خارجية.

سياق المشروع المشترك يأتي من الهدف وعناصر اللوحة المعتمدة أو المدخلة يدويًا، بحد 12000 حرف، بالإضافة إلى سياق المحادثة. لا تُرسل كل المحادثات الأخرى كاملة إلى كل طلب. اقتراح اللوحة يقرأ أحدث ثماني محادثات (حتى 12 رسالة من كل منها ثم آخر 24 رسالة إجمالًا)، حتى 3000 حرف من الرسالة وبحد 30000 حرف إجمالًا.


## ما أضيف في مرحلة الذاكرة

- اختيار نموذج المدير ومزوده (Groq / OpenRouter) محفوظ ويُستخدم فعليًا في التخطيط والتلخيص.
- حفظ إعدادات العمال والنظام وحسابات المستخدمين وسجل النشاط في قاعدة واحدة.
- حفظ الرسائل وردود نمل تلقائيًا، وإعادة فتح المحادثة ومتابعتها من صفحة «المحادثات».
- إرسال السياق السابق للمدير والوكلاء والتلخيص. تُحفظ المحادثة كاملة، ويُستخدم آخر 20 رسالة وبحد إجمالي يقارب 24 ألف حرف كسياق للنموذج؛ الرسالة الواحدة تدخل السياق حتى 6000 حرف.
- بقاء جلسة تسجيل الدخول بعد إعادة تشغيل الخادم إلى انتهاء صلاحيتها (24 ساعة) أو تسجيل الخروج.
- استيراد ملفات JSON القديمة مرة واحدة دون حذفها أو تغيير معرفات التحليلات.
- دعم SQLite وPostgreSQL مباشرة، دون اشتراط Supabase.

## تشغيل Windows

المتطلبات: Python 3.10 أو أحدث وNode.js 20 أو أحدث. افتح PowerShell داخل مجلد المشروع.

```powershell
Copy-Item .env.example .env
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r agent_system/requirements.txt
npm ci
```

افتح `.env` وأضف مفاتيح النماذج التي تستخدمها. إعداد `GEMINI_API_KEY` القديم لا يشغل هذا المحرك؛ المحرك يستخدم Groq وOpenRouter.

لتبقى قاعدة SQLite مستقلة عن مكان فك ضغط النسخة أو تحديث الكود، اختر مسارًا دائمًا في `.env`:

```dotenv
STORAGE_BACKEND=sqlite
NAML_DATA_DIR=C:/NAML-data
```

شغّل الخادم في نافذة PowerShell:

```powershell
.\.venv\Scripts\python.exe -m uvicorn agent_system.api.main:app --host 127.0.0.1 --port 8000
```

وشغّل الواجهة في نافذة ثانية:

```powershell
npm run dev:frontend
```

افتح `http://localhost:3000`. الحساب الافتراضي لأول تشغيل: `admin` / `admin123`، ويمكن تغيير كلمة المرور عبر `/api/auth/change-password`. إعدادات مدير الحساب في «الإعدادات»، وإعدادات الوكلاء والنظام في «إدارة النظام ← النماذج والإعدادات». تظهر رسالة بعد نجاح الحفظ.

تتضمن النسخة بناء الواجهة داخل `dist`؛ يمكنك أيضًا فتح `http://localhost:8000` بعد تشغيل الخادم، دون تشغيل Vite. بعد أي تعديل في الواجهة شغّل `npm run build` لتحديث `dist`.

## أين تُحفظ البيانات؟

SQLite الافتراضي: `agent_system/storage/naml.sqlite3`، أو `naml.sqlite3` داخل `NAML_DATA_DIR` الذي تحدده. قاعدة البيانات تشمل الإعدادات والمستخدمين والمحادثات والتحليلات؛ مفاتيح مزودي النماذج تبقى في متغيرات البيئة.

إغلاق المتصفح أو إعادة تشغيل التطبيق لا يحذف البيانات. عند تحديث المشروع احتفظ بنفس قاعدة البيانات أو بنفس اتصال PostgreSQL. على استضافة ذات نظام ملفات مؤقت، استخدم PostgreSQL أو قرصًا دائمًا؛ ملف SQLite داخل حاوية مؤقتة لا يكفي لحفظ البيانات بين عمليات النشر.

التشغيل المرفق يستخدم عملية API واحدة. إذا انقطع الخادم أثناء تحليل، يبقى السؤال محفوظًا، ويظهر بعد التشغيل أن التحليل توقف؛ يمكنك متابعة المحادثة برسالة جديدة. لا يعيد النظام تنفيذ الطلب المدفوع تلقائيًا. تشغيل عدة عمليات API يحتاج تنسيق المهام؛ اضبط `NAML_RECOVER_INTERRUPTED=false` عند ذلك بدل إيقاف مهام عمليات أخرى.

## استخدام PostgreSQL

أنشئ قاعدة فارغة باسم `naml` ومستخدمًا لديه صلاحية إنشاء الجداول. ثبّت المتطلبات ثم عدّل `.env`:

```dotenv
STORAGE_BACKEND=postgres
DATABASE_URL=postgresql://naml:YOUR_PASSWORD@127.0.0.1:5432/naml
```

تُنشأ جداول `naml_documents` و`naml_sessions` تلقائيًا. يستخدم التطبيق Psycopg 3 واتصالًا مباشرًا بالخادم. البيانات لا تعتمد على ملفات SQLite عند اختيار PostgreSQL. مع مزود قاعدة بيانات خارجي، استخدم رابط الاتصال وإعداد SSL الذي يقدمه المزود. إذا احتوت كلمة المرور على رموز خاصة، استخدم URL encoding لها في الرابط.

## ترحيل البيانات

أوقف التطبيق قبل الترحيل واحتفظ بنسخة احتياطية من مصدر البيانات.

**JSON القديم:** احتفظ بمجلد `agent_system/storage` القديم داخل النسخة الجديدة قبل أول تشغيل. تُستورد `settings.json` و`users.json` وسجل النشاط وسجل الإعدادات وملفات `sessions/*.json` تلقائيًا مرة واحدة لكل قاعدة مستهدفة. تحويل إعداد `STORAGE_BACKEND=json` القديم إلى `sqlite` مطلوب. الملفات القديمة لا تُحذف. ملفات JSON التالفة توقف الاستيراد بدل استبدالها بإعدادات افتراضية.

**SQLite إلى PostgreSQL:** جهّز الهدف الفارغ واضبط متغيرات `.env` على PostgreSQL، ثم شغّل الأمر قبل بدء التطبيق:

```powershell
.\.venv\Scripts\python.exe -m agent_system.migrate_database --from-sqlite C:/NAML-data/naml.sqlite3
```

الأمر ينسخ الإعدادات والحسابات والرموز والمحادثات والتحليلات داخل معاملة واحدة. إذا وجد بيانات تطبيق في الهدف، يرفض الكتابة ولا يغيّر المصدر.

**Supabase القديم:** اضبط الهدف الجديد على SQLite أو PostgreSQL، وأضف مؤقتًا `SUPABASE_URL` و`SUPABASE_SECRET_KEY` الخاصة بالمصدر إلى `.env`، ثم:

```powershell
.\.venv\Scripts\python.exe -m agent_system.migrate_database --from-supabase
```

ينسخ تحليلات جدول `sessions` على دفعات ويحتفظ بالمعرفات، ويمكن إعادة تشغيله دون تكرار التحليلات. إعدادات النسخة القديمة والحسابات موجودة في ملفاتها المحلية؛ تُستورد كما في خطوة JSON. لا تُحذف بيانات Supabase. احذف متغيرات المصدر بعد التأكد من نجاح الترحيل.

## Docker

```sh
cp .env.example .env
# Add provider keys, then:
docker compose up --build -d
```

يستخدم `compose.yaml` مجلد بيانات دائمًا عبر named volume. تحديث الصورة لا يحذف البيانات؛ حذف الـvolume يحذف قاعدة SQLite. الإعدادات المحفوظة في الصورة نفسها ليست بديلًا عن volume دائم. PostgreSQL متاح أيضًا باستخدام `DATABASE_URL` في `.env`.

## التحقق

```sh
python -m pip install -r agent_system/requirements-dev.txt
python -m pytest -q
npm run lint
npm run build
```

الاختبارات تستخدم قواعد مؤقتة ومحاكاة للنماذج، وتشمل إعادة تشغيل عملية جديدة، متابعة المحادثات، عزل المستخدمين، ترحيل JSON، تزامن الكتابات، وعدم نجاح الحفظ عند فشل التخزين. اختبار PostgreSQL الاختياري يستخدم خادمًا محليًا مؤقتًا عند تثبيت `pgserver` وتشغيل `python -m pytest tests/test_postgres.py -q`. في بيئة لا تسمح ببدء خادم محلي، يُتخطى هذا الاختبار؛ يمكن ضبط `NAML_TEST_POSTGRES_URL` على رابط قاعدة اختبار مخصصة بدلًا من ذلك.

اختُبر هذا الإصدار باستخدام SQLite وبنماذج محاكاة، مع اختبارات متصفح فعلية للحفظ والتنقل على الكمبيوتر والجوال. لم يُنفذ طلب فعلي إلى Groq أو OpenRouter بمفتاح مستخدم، ولم يُختبر اتصال PostgreSQL حي في هذه البيئة. التوازي يستخدم حتى أربعة وكلاء في الوقت نفسه بسياق أولي مشترك، والمراجعة النقدية قد تتبعها محاولة تصحيح واحدة.

عند التحديث، لا تستبدل مجلد بياناتك بمجلد فارغ؛ أوقف الخادم، احتفظ بملف `.env` وقاعدة البيانات، ثم استبدل ملفات التطبيق. لا تتضمن الحزمة مفاتيح سرية أو بيانات اختبارات. تبقى المشاريع والتفضيلات داخل نفس قاعدة البيانات الحالية، دون ترحيل يدوي.
